### 运控的关键认知

**核心是一条流水线，三个环节：**

```
        ┌── ① 步态调度 Gait Scheduler ──┐
        │  决定「什么时候哪条腿该动」      │
        │  trot/walk/pace 的相位表        │
        └───────────┬──────────────────┘
                    ↓ (phase, stance|swing)
        ┌── ② 足端轨迹 Foot Trajectory ─┐
        │  支撑相：贴地向后扫（推身体走）  │
        │  摆动相：抬起沿摆线回前         │
        └───────────┬──────────────────┘
                    ↓ (x, y, z) 足端目标
        ┌── ③ 逆运动学 IK ─────────────┐
        │  足端 → 三关节角（coxa/femur/  │
        │  tibia），每腿 3 DOF × 4 = 12  │
        └──────────────────────────────┘
```

**三类步态的取舍（实测相位表）：**

| 步态 | 相位偏移 | 占空比 | 同时着地 | 特点 |
|------|---------|--------|---------|------|
| **Trot** | LF/RR=0, RF/LR=0.5 | 0.5 | 2（对角） | 机器狗默认档，快且稳 |
| **Walk** | LF=0, RR=.25, RF=.5, LR=.75 | 0.75 | 3 | 四拍，最稳，适合负载 |
| **Pace** | LF/LR=0, RF/RR=.5 | 0.5 | 2（同侧） | 易侧翻，特殊场合 |

**Trot 为什么是默认**：对角两腿支撑时，重心投影落在对角连线上，形成稳定三角形；
速度快（半步周期），能耗低。Pace 同侧支撑，重心容易出界 → 侧翻。

### 逆运动学：踩过的坑（已修正）

我们最初的实现把膝角写成 `-θ3`，用正运动学反验发现**足端落点最大偏 99mm**。
正确约定：

```
θ3 = acos((L1² + L2² - D²) / (2·L1·L2))     ← 大腿-小腿「内角」，180° = 伸直
tibia_servo = θ3 - 180                        ← 舵机要的是「偏离伸直位的角度」
```

修正后正运动学反验误差 **0.00mm**（5 个测试点全对）。

> **教训**：逆运动学写完必须用正运动学反验。不验证的 IK 会在真机上表现为
> 「腿落不到该落的地方」，而现象看起来像舵机标定问题，极难排查。

### 舵机布局与标定

- 12 舵机（4 腿 × 3 关节），常用 PCA9685（I2C 16 通道）或 ESP32 LEDC（自带 PWM）
- 每条腿需要标定三项：**零位偏移**（offset）、**方向**（side ±1）、**限位**（range）
- OpenCat 的做法：把「站立中立位」的舵机值存为基准，所有动作相对它偏移

### 运控的关键认知

**轮子的数学比腿简单一个数量级**，但工程上更依赖闭环：

```
    运动学（开环）:
        v_left  = vx - ω · (wheel_base/2)
        v_right = vx + ω · (wheel_base/2)

    但开环跑不直 — 电池电压下降、地面摩擦、负载都会让实际速度偏离。
    所以标准做法是 PID 闭环:

        目标速度 → PID → PWM → 电机
                     ↑
                 编码器实测（每 20ms）
```

**必须做的三件事**：

1. **编码器闭环**：每个轮子一个 PID，`setpoint = 目标轮速`，`feedback = 编码器算的速度`
2. **里程计积分**：由左右轮实测速度反推位姿
   ```
   v = (v_l + v_r)/2,  ω = (v_r - v_l)/wheel_base
   θ += ω·dt,  x += v·cos(θ)·dt,  y += v·sin(θ)·dt
   ```
3. **IMU 融合**：编码器会累积漂移，用 IMU 的 yaw 校正（简单互补滤波就够）

### ROS2 生态的现实

如果要做复杂导航（SLAM/路径规划），走 **micro-ROS**：
ESP32 侧只当「电机+传感器驱动」，Nav2/建图都在上位机。
如果只是「语音让它走」，自研轻量协议（LDP）更省事——不必上 ROS。

| **ESP32-C3 桌面机器人** | 极低成本路线（AI 对话 + 鼠标控制 + 手机遥控） |

### 关键认知：桌面机器人的「生命感」从哪来

运动只有两个自由度（云台 pan/tilt），但**生命感不靠动作幅度，靠三件事**：

1. **表情**：圆屏上的眼睛（眨眼、瞳孔放大、视线跟随）——比机械动作更有效
2. **平滑**：所有动作走一阶低通，绝不生硬跳变（`pan += (target-pan)*0.25`）
3. **主动注意**：不是等人叫，而是自己转头看人（事件驱动的注视行为）

**PAD 情感模型**（MindPaw 用）：Pleasure / Arousal / Dominance 三维，
情绪状态驱动表情和动作幅度。这和我们 LAAP 认知引擎的情绪系统是同构的。

## 四、对话系统（四类机器人的共同底座）

### 参考项目

| 项目 | 许可证 | 核心 |
|------|--------|------|
| **78/xiaozhi-esp32** | MIT | ESP32 流式对话客户端，MCP 协议，最活跃 |
| **ESP-IoT-Solution `xiaozhi` 组件** | 乐鑫官方 | 双向流式对话组件，对接 xiaozhi.me |
| **ESP-SR** | 乐鑫 | 唤醒词（WakeNet）+ 语音识别（MultiNet） |
| **ESP-ADF** | 乐鑫 | 音频框架（codec / pipeline / 播放器） |

### 技术要点（xiaozhi 架构）

```
        麦克风 ──I2S──▶ 唤醒词(WakeNet) ──▶ 录音
                                              ↓
                                    Opus 编码（60ms 帧）
                                              ↓
                                        WebSocket 上行
                                              ↓
                                  服务端 ASR → LLM → TTS
                                              ↓
                                    Opus 下行 → I2S 播放
```

**关键工程细节**：

| 项 | 做法 | 为什么 |
|----|------|--------|
| 音频编码 | **Opus 60ms 帧** | 比 20ms 帧省带宽，比 120ms 帧延迟低 |
| 重采样 | 动态重采样适配不同硬件采样率 | 麦克风常是 44.1k/48k，服务端要 16k |
| 唤醒词 | 端侧 WakeNet 常驻 | 不上行音频，省流量、保隐私 |
| VAD | 端侧能量/语音检测断句 | 减少无效上传 |
| 全双工 | 支持打断（abort 消息） | 像打电话，不是对讲机 |

> 我们 LAAP 已有完整对应实现：`laaper/hub/xiaozhi_audio_stream.py`
> （Opus 编解码 + 能量 VAD + whisper ASR + edge-tts TTS + 帧间超时看门狗）

### 四类机器人的对话差异

| 类型 | 差异点 |
|------|--------|
| 机械狗 | 语音 + **动作反馈**（"坐下"= 真坐下 + 语音确认） |
| 机器车 | 语音 + **移动**（"去客厅"= 导航 + 到达播报） |
| 桌面宠物 | 语音 + **表情/注视**（说话时看着你，眨眼） |
| 桌面机器人 | 上述全部 + 屏幕显示字幕 |

## 五、提炼：LAAP 的统一抽象

把四类机器人的共性榨出来，得到三层：

### ① 运动抽象 `MotionController`

```python
move(vx, vy, omega)    # 速度：轮子/腿/云台都能接
pose(name)             # 命名姿态：stand/sit/wave/look_up
tick(dt)               # 控制周期推进 → 硬件指令
stop()                 # 急停
state()                # 状态回报
```

三类实现：
- `DifferentialDrive`（车）→ 输出左右轮目标速度（固件 PID 闭环）
- `QuadrupedMotion`（狗）→ 输出 12 个关节角（IK + 步态）
- `PanTiltController`（宠物）→ 输出 pan/tilt 角度（一阶低通）

### ② 协议 `LDP`（LAAP Device Protocol）

统一消息族：`hello / register / heartbeat / percept / motion.* / dialogue.* / state.report`

**核心设计**：LAAP 不说"给轮子 100 的 PWM"，只说：

```python
text_to_motion("往前走")   → {"cmd": "move", "vx": 150}
text_to_motion("坐下")     → {"cmd": "pose", "name": "sit"}
text_to_motion("看着我")   → {"cmd": "pose", "name": "look_up"}
```

具体是轮子转还是腿迈，由设备侧自己翻译。

### ③ 能力协商

设备上线声明自己能干什么，LAAP 据此决定派什么活：

```json
{
  "kind": "dog",
  "sensors": ["imu", "touch", "distance"],
  "actuators": ["motion"],
  "poses": ["stand", "sit", "home", "wave"],
  "motion": "quadruped",
  "joints": 12,
  "dialogue": true
}
```

宠物没有 `sit` 姿态 → LAAP 不会派"坐下"，而是降级成别的表达。

## 六、四类机器人选型建议

| 类型 | 主控 | 关键外设 | 难度 | 适合先做 |
|------|------|---------|------|---------|
| **桌面宠物** | ESP32-S3 | 圆屏(GC9A01) + 2 舵机云台 + I2S 麦/功放 | ⭐⭐ | ✅ 最推荐起步 |
| **机器车** | ESP32-S3 | 2 电机 + 编码器 + IMU + 超声 | ⭐⭐ | ✅ ROS 生态好 |
| **桌面机器人** | ESP32-S3 | 上述两者合并 | ⭐⭐⭐ | 第二阶段 |
| **机械狗** | ESP32-S3/P4 | 12 舵机(PCA9685) + IMU + 电池 | ⭐⭐⭐⭐ | 最后做（数学最多） |

**为什么宠物先做**：2 个自由度就能表达生命感，代码量小，最容易验证整条链路
（语音→意图→动作→反馈）是否通。狗要 12 个舵机同时正确，调试成本高一个数量级。
