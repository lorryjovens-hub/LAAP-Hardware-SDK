# LBP/1.0 — LAAP Body Protocol 规范

> 数字生命的物理地面。规定电压、引脚、编码、时序，也规定**身体如何被描述、
> 插拔后身体图式如何重建**。

---

## 0. 为什么需要这一层

LAAP 现有所有工作都在软件抽象层之上——即使 `laaper` 的感知算法再精确，
它碰到的也只是 OS/ROS 给它的数。LBP 补的是**从意图到电流之间缺失的那一段**。

同步澄清一个分层边界：

| 层 | 谁负责 | LBP 管不管 |
|----|--------|-----------|
| 认知 / 技能 / 反射（1Hz / 10Hz / 1kHz） | LAAP | 不管，只提供同步与时序基础 |
| 协议（帧/枚举/拓扑/身体图式） | **LBP** | 全管 |
| 线路编码 / 电压 / 连接器 | **LBP** | 全管 |
| 电机电流环 / PID | 模块内 MCU | **不管**（见 §3.3） |

**LBP 不定义电流怎么流，定义的是意图、时序与安全边界。**

---

## 1. 分层

对标 PCIe 的三层分解，增加 LAAP 独有的「身体层」：

```
┌─────────────────────────────────────────────────────────┐
│ L5 语义层  SEM      可供性 / 反射弧契约 / 技能注册         │  → 接 laaper
├─────────────────────────────────────────────────────────┤
│ L4 身体层  BODY     身体图式 / 拓扑 / 运动链 / 变形        │  ★ LAAP 独有
├─────────────────────────────────────────────────────────┤
│ L3 节点层  NODE     枚举 / BMD 自描述 / 地址分配           │
├─────────────────────────────────────────────────────────┤
│ L2 链路层  LINK     帧 / CRC32 / 分片 / 优先级 / 时钟      │
├─────────────────────────────────────────────────────────┤
│ L1 编码层  CODING   调制 / 线路编码 / 同步 / 扰码          │
├─────────────────────────────────────────────────────────┤
│ L0 物理层  PHY      电压 / 差分 / 连接器 / 供电 / 时序      │
└─────────────────────────────────────────────────────────┘
```

### 协议与介质解耦

帧格式统一，跑在不同物理介质上构成不同 **profile**：

| Profile | 介质 | 速率 | 用途 |
|---------|------|------|------|
| **LBP/CAN** | CAN FD 差分双绞 (ISO 11898-2) | 5 Mbps | 关节、电机、传感器 |
| **LBP/ETH** | 100BASE-TX / 1000BASE-T1 | 100M / 1G | 骨干、视觉、大算力 |
| **LBP/SPI** | 板内 SPI | 10-50 MHz | 显示屏、板载传感器 |
| **LBP/SIM** | 内存环回 | — | 开发测试（本文代码的默认） |

## 2. L0 物理层

### 2.1 供电母线 LBP/PWR

| 项 | 规格 | 依据 |
|----|------|------|
| 母线电压 | **48 V DC**（36–56 V） | 同功率下电流为 24V 的一半、12V 的四分之一；I²R 损耗降 16×；< 60V 属 SELV 安全特低电压 |
| 单模块峰值 | ≤ 20 A（960 W 瞬时） | 对应腿部落地冲击 |
| 连接器 | **三段式**：GND → PWR → 信号 | 防打火。顺序反了会烧触点 |
| 热插拔 | 必须 hot-swap 控制器（TPS24720 / LTC4364） | 把浪涌限制在 2× 额定内；否则插入瞬间母线塌陷，全线模块重启 |
| 隔离 | 每模块 DC-DC 隔离 1.5 kV | 单点短路不拖垮母线 |
| 母线电容 | `C ≈ I_peak / 48 × 2 ms` | 2 ms 掉压容限（见 `power_summary()`） |

### 2.2 关节总线 LBP/CAN（L0/L1）

| 项 | 规格 |
|----|------|
| 标准 | ISO 11898-2 CAN FD |
| 速率 | 仲裁段 1 Mbit/s，数据段 **5 Mbit/s** |
| 差分电压 | 显性(0)：CAN_H − CAN_L = **2.0 V**；隐性(1)：**0 V** |
| 共模电压 | **2.5 V**（收发器内部偏置） |
| 终端 | 总线两端各 **120 Ω**，中间节点不接 |
| 最大节点 | 64 |
| 最大长度 | 40 m @ 1 Mbps；**10 m @ 5 Mbps** |
| 线路编码 | **NRZ + 位填充**：5 个连续同电平后插 1 个反相位（CRC 域例外） |
| 帧 ID | 标准帧 11-bit（推荐：高 3 bit 放优先级，便于仲裁） |

### 2.3 骨干 LBP/ETH（L0/L1）

| 项 | 100BASE-TX | 1000BASE-T1 |
|----|-----------|-------------|
| 介质 | 2 对 Cat5e | **1 对**差分（车规） |
| 线路编码 | 4B/5B + MLT-3 | **PAM3**（3 电平） |
| 符号率 | 125 MBd | 750 MBd |
| 差分摆幅 | ±1 V | ±1 V |
| 连接器 | RJ45 / M12 | Hirose GT25 |
| 最大长度 | 100 m | 15 m |
| 隔离 | 变压器 1.5 kV | 变压器 |

### 2.4 同步线 LBP/SYNC

| 项 | 规格 |
|----|------|
| 电平 | 3.3 V LVCMOS |
| 信号 | **1 kHz 硬件脉冲**，各模块中断输入 |
| 抖动 | < 100 ns |
| 作用 | 所有关节同一时刻更新目标位置，消除总线传输延迟导致的相位差 |

这是 EtherCAT 分布式时钟（DC）的最简化实现。**没有它，多足步态的关节协同
会出现 1–2 ms 相位误差，肉眼可见地不协调。**

### 2.5 机械对接端口

每个端口除电源与总线外，另有 **4 根检测线**：

| 线 | 作用 |
|----|------|
| `PORT_ID[0:2]` | 3-bit 位置编码（0–7），上拉 + 模块侧跳线 |
| `PRESENT#` | 在位检测，插入时拉低 |

**拓扑发现靠这 4 根线**：A 的 port2 检测到在位，读 ID 得 0 → 对端是 B 的 port0。

## 3. L1/L2 时序与帧

### 3.1 帧格式（medium-independent）

```
偏移  长度  字段      说明
─────────────────────────────────────────────────────────
0     1     SOF       0x4C ('L')
1     1     VER       [7:4]major [3:0]minor → 0x10 = 1.0
2     1     TYPE      消息类型
3     1     FLAGS     [7]分片 [6:5]优先级 [4]需应答 [3:0]保留
4     1     SRC       源模块 ID（1-254，0=未分配，255=广播）
5     1     DST       目标模块 ID
6     2     SEQ       序号（LE，用于去重/重传）
8     1     TTL       跳数限制（防环）
9     3     RSVD      保留（对齐）
12    4     T_EXEC    执行时间戳（µs, LE）
16    2     LEN       载荷长度（0–1024）
18    N     PAYLOAD
18+N  4     CRC32     CRC-32/ISO-HDLC，覆盖 VER..PAYLOAD
22+N  1     EOF       0xAA
─────────────────────────────────────────────────────────
```

**CAN 上的实际容量**：整帧 ≤ 64 B → 载荷 ≤ `64 − 18 − 5 − 4(分片头) = 37` B。
（`Fragmenter` 的参数是整帧字节数，不是载荷长度——这里容易搞错。）

### 3.2 T_EXEC 执行时间戳（核心机制）

不是「立即执行」，是「在全局时刻 T 执行」。

```
主机                    关节 A          关节 B          关节 C
 │  CMD t_exec=T ────────▶│               │               │
 │  CMD t_exec=T ────────────────────────▶│               │
 │  CMD t_exec=T ────────────────────────────────────────▶│
 │                        │ (等待)        │ (等待)        │
 │                   ─────┴───────────────┴───────────────┴───── T
 │                        同时动作
```

所有关节收到同一批指令，各自等到 T 那一刻同时动作。**这解决了分布式控制的
相位同步问题，也是 10 Hz 技能层能协调 20 个关节的原因。**

### 3.3 反射弧必须在模块内（硬约束）

带宽核算（`bandwidth_estimate()`）：

```
技能层 10 Hz、20 关节：
  CMD   20 × 10 × (32+23)×8 = 88 kbps
  TELEM 20 × 10 × (40+23)×8 = 101 kbps
  合计 190 kbps → 占 5 Mbps 的 3.8%     ✓ 余量巨大

反射层 1 kHz、20 关节：
  20 × 1000 × 55B × 8 = 8.8 Mbps > 5 Mbps   ✗ 超载 378%
```

**结论：反射弧不可能走总线。** 总线下发目标位置/力矩 + 安全边界，
模块自己的 MCU 在 10–20 kHz 跑电流环。碰撞回撤这类反射由模块自行触发，
事后用 `REFLEX` 上报。

这不是优化选择，是物理约束。

### 3.4 优先级

| 优先级 | 值 | 消息 | 时延要求 |
|--------|----|------|---------|
| `SAFETY` | 0 | `SAFE_STOP` / `REFLEX` | < 100 µs |
| `CONTROL` | 1 | `CMD` / `TELEM` | < 10 ms |
| `CONFIG` | 2 | `ENUM` / `TOPO` / `BODY_SCHEMA` | < 1 s |
| `BULK` | 3 | `OTA` / 大载荷分片 | 尽力 |

**`SAFE_STOP` 必须在链路层就能插队**，不能等软件队列——等它排到前面时，
关节已经撞上了。CAN 的 ID 仲裁天然支持；以太网靠 Q-Tag / 时间片。

### 3.5 消息类型

| 值 | 类型 | 方向 | 说明 |
|----|------|------|------|
| 0x01 | `ENUM_REQ` | 主机→广播 | 枚举，分配地址 |
| 0x02 | `ENUM_ACK` | 模块→主机 | 应答 + 完整 BMD |
| 0x03 | `CAPS` | 模块→主机 | 能力变更上报 |
| 0x04 | `CMD` | 主机→模块 | 运动指令（带 T_EXEC） |
| 0x05 | `TELEM` | 模块→主机 | 遥测 |
| 0x06 | `CLOCK_SYNC` | 主机→广播 | 时钟同步 |
| 0x07 | `TOPO_REQ` | 主机→模块 | 查询端口连接 |
| 0x08 | `TOPO_ACK` | 模块→主机 | 端口连接应答 |
| 0x09 | `BODY_SCHEMA` | 主机→广播 | 广播身体图式 |
| 0x0A | `REFLEX` | 模块→主机 | 反射事件 |
| 0x0B | `SAFE_STOP` | 任意→广播 | **最高优先级** |
| 0x0C | `FRAG` | 双向 | 分片 |
| 0x0D | `HEARTBEAT` | 双向 | 心跳 |
| 0x0E | `OTA` | 主机→模块 | 固件升级 |

### 3.6 载荷编码：小端二进制，不是 JSON

这一条是实测踩出来的。早期实现对 `TOPO_ACK` 用 JSON：

```json
{"addr":2,"mount_port":0,"children":[]}
```

整帧 **67 字节，超过 CAN 2.0B 的 64 字节上限，根本发不出去**。
同样的信息用二进制只要 **3 字节**。

**所有载荷统一用固定布局小端二进制**（对应 C 的 `#pragma pack(1)` 结构体）：

| 消息 | 布局 | 典型大小 |
|------|------|---------|
| `TOPO_ACK` | `addr(1) mount_port(1) child_count(1) [port(1) child(1)]×N` | 3 B（无子模块） |
| `CMD` | `flags(1) dof(1) q(f32)×dof` | 14 B（3 DOF） |
| `TELEM` | `addr(1) flags(1) dof(1) q(f32)×dof [torque(f32)×dof] [temp(i8)]` | 15–31 B |
| `REFLEX` | `addr(1) code(1) joint(1) value(f32)` | 7 B |
| `CLOCK_SYNC` | `t1_us(u64)` | 8 B |

带宽对比（20 关节 @ 100 Hz）：

```
JSON   CMD 约 30B 载荷 → 帧 53B → 848 kbps
二进制 CMD 12B 载荷  → 帧 35B → 560 kbps    ← 省 34%
```

实现：`laaper/body/payload.py`，对应的 C 结构体可直接对齐。

#### 单个模块最多能有多少自由度（CAN 2.0B 下）

```
 8 DOF → 帧 57B   OK
 9 DOF → 帧 61B   OK
10 DOF → 帧 65B   ← 超限，需分片
```

所以 **单个从站模块的自由度超过 9 就要分片下发 CMD**。
这意味着模块拆分粒度应该控制在 **≤ 9 DOF**：

| 模块 | DOF | 单帧下发 |
|------|-----|---------|
| 3-DOF 腿 | 3 | ✓ |
| 4-DOF 臂 | 4 | ✓ |
| 6-DOF 臂 | 6 | ✓ |
| 12-DOF 四足一体 | 12 | ✗ 需分片 |

这是把「一条腿」做成一个独立节点的另一个理由：**不只是热插拔方便，
也是为了让 CMD 能单帧下发**。

### 3.7 分片必须携带原始消息类型

分片后的帧 `type` 都是 `FRAG`，**原始类型会丢**。
接收方重组完只知道「这是一堆字节」，不知道该按 BMD 还是固件处理。

所以分片头必须带原类型：

```
group_id(2) index(1) total(1) msg_type(1)    ← 5 字节
```

因此 CAN 上的真实容量是 `64 − 18 − 5 − 5 = 36` 字节/片。

> 这个 bug 的表现极隐蔽：数据能完整重组出来，但因为不知道类型，
> 上层直接丢掉。**没有行为测试根本发现不了。**

### 3.8 时钟同步

四时间戳 PTP（`ClockSync.update(t1,t2,t3,t4)`）：

```
delay  = ((t2−t1) + (t4−t3)) / 2
offset = ((t2−t1) − (t4−t3)) / 2
```

| 层 | 目标精度 | 手段 |
|----|---------|------|
| 骨干 | < 1 µs | gPTP |
| 关节 | < 10 µs | CAN 硬件时间戳 + 周期 SYNC |

1 kHz 反射周期 = 1000 µs，10 µs 抖动占 1%，可接受。

## 4. L3 节点层：BMD 模块自描述

### 4.1 和 USB Descriptor 的根本差别

USB descriptor 描述「接口」：端点数量、传输类型、功率。
它不关心这个设备在物理世界是什么形状。

BMD 描述「身体部件」：**几个自由度、连杆多长、质心在哪、最大力矩多少、
接口朝向如何**。

| 字段 | 为什么必需 |
|------|-----------|
| `joints[].axis` + `link` | 自动 FK/IK |
| `mass_kg` + `com_offset` | 自动算装配质心 → 平衡判断 |
| `ports[].normal` + `offset` | 自动推拓扑 + 挂载坐标系 |
| `power_peak_mw` | 决定母线电容 / 线径 |
| `serial` | 身份锚定（同一意识换身体后仍认得） |

### 4.2 字段

```c
typedef struct {
    uint32_t magic;              // 'L','B','M','D'
    uint8_t  ver_major, ver_minor;
    uint8_t  cls;                // 0x01执行器 0x02传感器 0x03算力 0x04电源 0x05结构 0x06轮式
    uint8_t  role;               // 0x01脊柱 0x02肢体 0x03关节 0x04末端 0x05眼 0x06耳 0x07皮肤 0x08脑 0x09轮 0x0A嘴
    uint16_t vendor_id, product_id;
    uint64_t serial;

    uint8_t  dof;
    float    link_len_m[4];
    float    joint_min_rad[6], joint_max_rad[6];
    float    max_vel_rad_s[6],  max_torque_nm[6];
    float    payload_kg, reach_m;
    float    mass_kg;
    float    com_offset[3];

    uint8_t  bus_profile, bus_addr;
    uint16_t power_mw, power_peak_mw;

    uint8_t  port_count;
    struct { uint8_t pos_id; uint8_t orientation; float mount_offset[3]; } ports[8];

    bool     hw_timestamp;
    int32_t  clock_offset_ns;
    uint32_t caps;
    char     name[32];
} lbp_bmd_t;
```

JSON 序列化后约 660 B，CAN 上需 18 帧（37 B/帧）。

### 4.3 枚举流程

```
主机                          模块
 │  ENUM_REQ (broadcast) ────▶│
 │                            │ 分配地址、回 BMD
 │◀── ENUM_ACK (FRAG×N) ──────│
 │  ... 重复至所有模块就绪 ...  │
 │  TOPO_REQ ────────────────▶│
 │◀── TOPO_ACK (端口连接表) ───│
 │  BODY_SCHEMA (broadcast) ─▶│
```

## 5. L4 身体层：拓扑与身体图式

### 5.1 核心设计：物理拓扑就是语义

USB 枚举把「插在哪个口」当寻址信息。
LBP 把「插在哪个口」当成**身体结构**：

```
底面四角  → 四条腿  → 四足
左右两侧  → 两条臂  → 能抓东西
四角四轮  → 四轮    → 车
```

**协议不需要知道"我是四足"，它只要知道谁接在哪，身体图式是推导出来的。**

### 5.2 推导流程

```
拓扑图 → 找根(POWER/COMPUTE) → DFS 建链 → 聚合关节/几何
                                      ↓
                                   FK 算末端
                                      ↓
              质心 / 支撑多边形 / 稳定裕度 / 能力位 / 运动模式
```

### 5.3 坐标系约定

世界系：**X 前、Y 左、Z 上**（右手系）

端口系（child 模块的局部系）：
```
Z = port.normal（朝外）
X = normalize(cross(world_up, Z))；Z 与 up 平行时退化取 (1,0,0)
Y = cross(Z, X)
```

FK：
```
T = T_base · Π [ Translate(j.offset) · Rot(j.axis, q) · Translate(j.link) ]
```

### 5.4 稳定性判据

| 着地点数 | 判据 |
|---------|------|
| ≥ 3 | 支撑多边形凸包；**稳定裕度 = 质心投影到最近边的距离**；要求 > 15 mm |
| 2 | 天生不稳定，标记 `requires_active_balance`（需 IMU + 力矩闭环） |
| ≤ 1 | 站不住 |

**着地点判定必须是几何的，不能只看角色**：

```python
# 错：role 是 wheel 就算着地
# 对：
return tip_z <= ground_z + tol      # tol: 肢/轮 40mm，其它 20mm
```

反面案例：四足侧面插两个轮，轮末端在 z=+0.02，比足端高 27 cm。
只看角色会算出「6 点支撑 假稳定」，真机上一松手就倒。

### 5.5 变形校验

`MorphEngine` 在动作**之前**校验：

| 检查 | 拒绝条件 |
|------|---------|
| 功率预算 | 峰值功率 > 母线预算 |
| 静态稳定 | ≥3 点支撑且裕度 < 15 mm |
| 可站立性 | ≤1 点支撑 |
| 移动能力 | 原本能移动，变形后不能 |

**任何一项不过 → 回滚，拒绝这次变形**，并说明原因。

### 5.6 支撑切换（真实换件的必要条件）

四足拆掉一条支撑腿，剩余三点且质心偏移，**物理上就是会倒**。
真实机器人换腿必须先趴下或上支架。

协议提供 `assume_supported=True`：跳过静态稳定性检查（重量不再由腿承担），
但功率与移动能力检查仍然生效，且完成后提示「需重新校验能否自主站立」。

**这不是偷懒的开关，是对物理约束的诚实建模。**

```
四足: 4×leg  12DOF  1.57kg  峰值38W  quadruped  裕度+39.0mm  稳定
两足+双臂: 2×leg 2×arm  14DOF  1.85kg  biped  需主动平衡  MANIPULATION
四轮: 4×wheel  4DOF  1.09kg  differential  裕度+60.0mm  稳定
四轮+单臂: 质心 y=+108mm → 裕度 -28.4mm → 协议报警
```

### 6.3 五条从测试里学到的教训

**① 分片的参数语义**
`max_payload=64` 是错的——64 是**整帧**上限。按前者算会得出「一帧 82 B」，
CAN 上根本发不出去。正确参数名应叫 `max_frame_bytes`。

**② 着地点必须按 z 坐标判，不能按角色**
侧向装的轮子离地 27 cm 却被算成支撑点，得出假稳定的身体图式。

**③ 分片丢掉了原始消息类型**
重组出 663 字节却不知道它是 `ENUM_ACK`，上层只能丢弃。
分片头补上 `msg_type` 后解决（§3.7）。

**④ 载荷不能用 JSON**
`TOPO_ACK` 用 JSON 整帧 67 B → 超过 CAN 64 B 上限，发不出去。
改小端二进制后 3 B（§3.6）。

**⑤ 协议能区分「拔哪条腿」**
质心偏后 −24 mm，所以：
- 拔后右腿 → 三足裕度 **5.8 mm** → 拒绝
- 拔前左腿 → 三足裕度 **28.1 mm** → 允许

同一台四足，几何不同，结论不同。这比「一律拒绝」有用得多。

## 7. 诚实边界

### ✅ 协议层已实现并验证

帧编解码 / CRC / 分片 / 优先级 / 时钟同步 / 带宽核算 / BMD /
拓扑发现 / 运动链 / 自动 FK·IK / 支撑多边形 / 稳定裕度 /
身体图式推导 / 变形校验与回滚 / 功率核算

### ⚠️ 硬件未验证

| 项 | 状态 |
|----|------|
| 48V 母线 + hot-swap | 只有设计，未做板 |
| CAN FD 关节总线 | 只有帧层，未接真实收发器 |
| 3 针端口 ID 拓扑发现 | 只在软件模拟 |
| 硬件同步线 | 未做 |
| 机械对接结构 | 未做（难度最高的部分） |

### ❌ 物理上的真正难点

| 挑战 | 现实约束 |
|------|---------|
| **对接精度** | 磁吸重复精度 ±0.2 mm；亚毫米需锥面定位 + 锁销 |
| **结构刚性** | 每个对接面都是刚度薄弱点，串联 5 个模块末端偏移累积到厘米级 |
| **触点寿命** | 弹簧触点 1–10 万次插拔 |
| **功率密度** | 6-DOF 臂峰值 500 W / 48 V = 10 A |
| **成本** | 每模块接口（车规连接器 + hot-swap + 隔离 DC-DC）约 ¥200–500 |

**这些不是协议问题，是机械和功率问题。** 协议能做的是让「插上什么，
软件立刻知道自己是什么、能不能站、能干什么」——这一半已经完全落地。

## 8. 与现有 LAAP 的堆叠关系

```
LAAP 认知层（PSI / 记忆 / 意识流帧）        1 Hz     ← 已有
LAAP 技能层（规划 / 可供性）                10 Hz    ← 已有
★ LBP L4-L5（身体图式 / 可供性契约）                 ← 本文档
★ LBP L2-L3（帧 / 枚举 / BMD）                       ← 本文档
★ LBP L0-L1（电压 / 编码 / 时序 / 连接器）            ← 本文档
反射层（模块内 PID）                    1–20 kHz  ← 模块固件
```

**LBP 不替代 LDP。** LDP 是「要做什么」（应用语义），
LBP 是「怎么把信号送到」+「身体现在是什么形状」。两者是堆叠，不是替代。
